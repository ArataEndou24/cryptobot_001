# 制約条件の分析: 日本在住・小資金・LINE 通知（v0.1）

ユーザー回答（日本国籍・日本在住、初期資金 700 USD、許容 DD 50%、レバレッジおまかせ、通知は LINE Messaging API）が
設計に与える影響を整理します。**法規制・各取引所の受入状況は変わりやすいため、実口座を開く前に必ず最新情報を確認してください。**

---

## 1. 日本在住が取引所選択に与える影響（D-01）

### 1.1 事実関係（2026 年時点の一般的な理解。要再確認）
- 日本の金融庁（FSA）は、無登録で日本居住者にサービスを提供する海外取引所に対して警告を出しています。**警告の対象は事業者**であり、利用者が処罰される規定ではありませんが、以下の実務リスクがあります。
  - 取引所側が突然「日本居住者の新規受入停止」「既存口座の制限・強制クローズ」を行う可能性（過去に Binance Global が日本居住者を Binance Japan へ移行させた例）。
  - 日本円の入出金経路が限られ、資金移動に時間とコストがかかる。
- **国内の登録業者（bitFlyer, GMO コイン, Coincheck 等）**: 法的に最も安全。ただし
  - 証拠金取引のレバレッジ上限は **2 倍**（金融庁規制）。
  - 無期限先物は基本なく、CFD 型のレバレッジ取引（bitFlyer Lightning FX など）が代替。
  - 最小注文数量が比較的大きい（例: BTC 0.01 単位）。**700 USD では 1 ロットすら建てられない、または 1 ロットが全資金になる**可能性が高く、分散も段階的サイジングも不可能。
  - API のレート制限・板データ配信が海外大手より弱い。

### 1.2 候補比較

| 候補 | 法的安全性 | 流動性・API | 最小ロット（700 USD との相性） | ショート／funding | 総合 |
|---|---|---|---|---|---|
| (a) 国内取引所の CFD（bitFlyer Lightning FX 等） | ◎ | △ | ✕（最小 0.01 BTC 級で資金に対して過大） | ○ / SFD あり（funding とは性質が異なる） | 現段階では資金規模の面で不適 |
| (b) 海外 CEX の USDT 無期限（Bybit, OKX, Bitget 等） | △（FSA 警告あり。受入状況が変動） | ◎ | ○（最小 5〜10 USDT 相当が多い。BTC は 0.001 単位のため銘柄によっては粗い） | ◎ | 技術的には最適。制度リスクを受容できるかが論点 |
| (c) 分散型無期限（Hyperliquid 等の DEX） | △（登録制度の外。自己管理ウォレット） | ○（API は良好。流動性は主要銘柄なら十分） | ◎（最小 10 USD 程度） | ◎ | 小資金と相性が良い。秘密鍵管理・ブリッジ・スマートコントラクトのリスクが加わる |
| (d) 国内現物のみ | ◎ | △ | △ | ✕（ショート不可、funding なし） | 戦略の半分（キャリー、ショート）が使えない |

### 1.3 推奨
- **主戦場**: (b) または (c)。技術設計はどちらでも動くよう、**取引所アダプタを抽象化し、最初から 2 系統（CEX 系と DEX 系）の実装を想定**する。
- **研究用データ**: Binance の公開履歴データ（無料・高品質・USDT 無期限の全銘柄）を使う。データ取得は取引ではないので居住地の制約を受けない。取引所固有のコスト（手数料・スリッページ）は執行先のデータで別途キャリブレーションする。
- **[要決定 D-01]** ユーザーが (b) と (c) のどちらの制度リスクを受容するか。私の推奨は「**まず (b) Bybit の USDT 無期限でテストネット→少額本番、並行して (c) を第 2 系統として実装**」。理由: (b) は API・ドキュメント・テストネットが整っており開発が速い。(c) は分散のため。

### 1.4 税務メモ（設計に影響する範囲のみ）
- 暗号資産の売買益・デリバティブ益は原則 **雑所得（総合課税、最大 55%）**。FX のような申告分離課税（20%）は適用されない（2026 年時点、税制改正の議論あり）。
- 損失の翌年繰越ができない。
- 影響: 高頻度の取引でも損益計算は「年間通算」で行うため、**全約定の完全な記録（時刻・数量・価格・手数料・円換算レート）**を保存する必要がある。設計書 9.3 のログ要件に「税務計算に足る粒度」を加える。

## 2. 初期資金 700 USD が設計に与える影響（D-04）

### 2.1 何が変わるか
- **最小ロットの粗さが最大の制約**。BTC 無期限の最小数量が 0.001 BTC の場合、その名目額が資産に対して大きすぎ、ポジションを「0 か 1 か」でしか持てない。連続的なサイジング（ボラ目標、確信度）が機能しない。
  - 対策 1: 初期ユニバースを **ETH など最小名目額が小さい銘柄** に寄せる（D-02 を「BTC+ETH」から「ETH 中心＋最小名目額が小さい上位銘柄」へ見直す）。
  - 対策 2: サイジングを **離散（0 / 1 / 2 ロット）** で設計し、バックテスターも同じ離散制約で評価する。
- **手数料は相対で効く**ので資金の大小で有利不利はないが、**取引所の最小手数料・出金手数料**は絶対額のため、小資金では相対的に重い。出入金回数を最小化する。
- **統計的検証に影響なし**: 研究は名目 1 単位で行い、離散化の影響は別途シミュレーションする。
- **この段階の目的は「利益額」ではなく「システムの正しさの実証」**。700 USD での 3 か月は、バックテストと実運用の乖離、執行品質、運用安定性を測るためのコスト。増資判断はその結果に基づく。

### 2.2 スケール計画
| 段階 | 資金 | 条件 |
|---|---|---|
| S0 | テストネット（仮想資金） | 1 週間無人稼働、照合乖離ゼロ |
| S1 | 700 USD | 3 か月。実スリッページがバックテスト想定の 1.2 倍以内、稼働率 99.5% |
| S2 | 増資（ユーザー判断） | S1 の結果と目標指標（設計書 0 章）の達成状況で判断 |

## 3. 許容 DD 50% とレバレッジ（D-09, D-10）

### 3.1 DD ラダー（決定）
| 累積 DD | 動作 |
|---|---|
| −20% | 全戦略の規模を半減 |
| −35% | 規模を 1/4 に |
| −50% | 全停止。人間の承認なしに再開しない |

- DD は「直近最高資産からの下落率」。テストネット／本番で別々に管理。
- 50% は「資金の半分を失っても続行する」という宣言です。統計的には、年率ボラ 40% の戦略でも 50% DD は稀にしか起きませんが、**取引所リスク（破綻・出金停止）は DD ラダーで防げない**ことに注意。

### 3.2 レバレッジ（提案 → Decided）
- **総レバレッジ上限: 3 倍**（ハードキャップ。リスクゲートで強制）
- **通常運転**: 年率ボラ目標 **40%** でサイジング。主要銘柄のボラ（年率 50〜80%）に対して概ね 0.5〜1.5 倍のエクスポージャーになる。
- **単一銘柄上限**: 資産の 100%（小資金・少銘柄のため集中を許容。S2 以降で 30〜50% へ引き下げ）
- 理由: 3 倍超は清算リスクが急増し、「DD 50% で停止」の前に清算で全損する経路ができる。清算価格は常に DD 停止水準より遠くにあるよう、レバレッジ上限から逆算する（3 倍なら約 −33% で清算のため、実際には **維持証拠金込みで 2.5 倍以下**に自動制限する）。

## 4. LINE Messaging API 通知（D-14）

### 4.1 前提
- LINE Notify は 2025 年 3 月末に終了済み。Messaging API の **push message** を使う。
- 必要なもの: LINE Developers でプロバイダー／Messaging API チャネル作成、**チャネルアクセストークン（長期）**、通知先の **userId**（ボットを友だち追加してから webhook または「あなたのユーザー ID」で取得）。
- **無料枠は月 200 通程度**（プランにより変動。要確認）。無制限に送るとすぐ枯渇する。

### 4.2 設計
- 重大度別ルーティング:
  - **P0**（キルスイッチ、DD 閾値、照合乖離、ハートビート途絶）: 即時 push。重複抑止（同一事象は 10 分に 1 通）。
  - **P1**（データ遅延、レート制限、リジェクト連続）: 5 分間バッファして 1 通にまとめる。
  - **P2**（日次レポート、品質レポート）: 1 日 1 通の要約。
- **月間送信予算**をローカルで管理（例: 150 通）。残量が 20% を切ったら P1 以下を停止し、P0 のみ送る。予算枯渇時の**フォールバックにメール**（無料・無制限）を用意。
- 通知内容にはポジション・損益・原因・推奨アクションを 1 画面に収める。
- トークンは環境変数（`LINE_CHANNEL_ACCESS_TOKEN`, `LINE_TARGET_USER_ID`）。リポジトリに置かない。
- 送信失敗（HTTP 429/5xx）は指数バックオフで再試行し、それでも失敗したらローカルログに残す。「通知が届かない」ことを検知するため、**毎朝の定時ハートビート 1 通**を送る（届かなければ通知系の障害）。
