# 暗号資産自動売買アルゴリズム 設計書（v0.1 ドラフト）

> 本書は「世界一の暗号資産自動売買アルゴリズム」を目指すプロジェクトの基本設計書です。
> 完全新規。既存コード・過去の資産は一切参照していません。
> 各節の末尾にある **[要決定]** は、ユーザーと合意すべき論点です（`01_DECISIONS.md` に集約）。

## 0. 「世界一」を測定可能な目標に落とす

「世界一」は感情的な言葉なので、そのままでは設計に使えません。以下の測定可能な目標に翻訳します。

| 指標 | 目標（本番運用時・全コスト控除後） | 備考 |
|---|---|---|
| 年率シャープレシオ（OOS） | 2.0 以上 | アウトオブサンプル（未学習期間）で。バックテスト内の数字は評価対象外 |
| 最大ドローダウン | 資産の 15% 以内 | 超過時は自動停止（第7章） |
| Calmar レシオ（年率リターン/最大DD） | 2.0 以上 | |
| 月次勝率 | 65% 以上 | |
| 稼働率 | 99.5% 以上 | 取引所障害を除く |
| 実現スリッページ | バックテスト想定の 1.2 倍以内 | 「バックテストと実運用の乖離」を継続監視 |
| 容量（キャパシティ） | 少なくとも運用資金の 10 倍まで性能劣化なし | 小資金でしか動かない戦略は「世界一」ではない |

### 0.1 設計思想（優先順位）

1. **生き残ること** — 破産確率を実質ゼロにする。リターンはその次。
2. **検証の誠実さ** — 過学習・先読み・データスヌーピングを構造的に排除する。バックテストで良く見えるのは簡単で、実運用で勝つのは難しい。
3. **執行品質** — 良いシグナルも手数料とスリッページで消える。執行はシグナルと同格の一級市民。
4. **複数エッジのアンサンブル** — 単一戦略に依存しない。相関の低い複数の収益源を束ねる。
5. **運用性** — 24/365 無人稼働。障害時に安全側へ倒れる。

## 1. 前提条件と主要決定事項

以下は設計全体を左右するため、最初に合意が必要です。**推奨案**を併記します。

### 1.1 取引市場
- **推奨**: 海外大手取引所の **USDT 建て無期限先物（パーペチュアル）** を主戦場にする。
  - 理由: 流動性が最も厚い／ショート可能／資金調達率（funding）という独立したエッジ源がある／API が成熟している／メイカー手数料が低い（あるいはマイナス）。
- 現物は「資産保管」と「一部戦略（現物・先物ベーシス裁定）」で補助的に使用。
- 日本国内取引所（bitFlyer, Coincheck, GMO 等）は、流動性・手数料・API 品質の面で主戦場には不向き。ただしユーザーの居住地・法規制・税務によっては国内取引所が必須になる可能性あり。
- **[要決定 D-01]** 取引所とアカウント種別（居住地の制約を含む）

### 1.2 取引銘柄
- **推奨**: 第1段階は **BTC, ETH** の 2 銘柄に集中。第2段階で流動性上位 20〜30 銘柄へ横展開（クロスセクション戦略を有効化）。
- 銘柄ユニバースは「過去 30 日平均の日次出来高」で動的に選定し、生存者バイアスを避けるため上場廃止銘柄もデータ上は保持する。
- **[要決定 D-02]** 初期ユニバース

### 1.3 時間軸（最重要）
- HFT（マイクロ秒〜ミリ秒）は、コロケーション・専用インフラ・チーム体制が必要で、個人〜小規模では勝負にならない。**除外**。
- **推奨**: **中頻度（Mid-Frequency）**
  - シグナル計算粒度: 1 分〜1 時間バー ＋ ティック／板から作る特徴量
  - 保有期間: 数十分〜数日
  - 1 日あたりの取引回数: 銘柄あたり 数回〜数十回
  - 理由: このゾーンは「HFT 勢はやらない（遅い）」「裁量トレーダーは統計的に扱えない（速い・多い）」という競争の隙間であり、手数料負けせず、かつ統計的検証に必要なサンプル数が確保できる。
- **[要決定 D-03]** 時間軸

### 1.4 資金規模
- 資金規模で戦略の選択肢が変わる（小資金なら板の薄い銘柄の非効率も取れる、大資金なら容量重視）。
- **[要決定 D-04]** 初期運用資金と将来の目標規模

### 1.5 技術スタック
- **推奨**: **Python 3.12** で研究・実行の両方を構築。パフォーマンスが問題になる箇所（バックテストの内側ループ、特徴量計算）は Numba／Polars で対処。Rust 化は「必要になってから」。
  - 理由: 研究の反復速度がすべて。Rust から始めるとエッジ探索が遅くなる。中頻度なら Python の遅延（数十 ms）は問題にならない。
- **[要決定 D-05]** 言語・スタック

### 1.6 稼働環境
- **推奨**: 取引所のマッチングエンジンに近いリージョンの VPS（例: 東京 or シンガポール）。ベアメタルは不要。
- **[要決定 D-06]** ホスティング

### 2.1 レイヤー分割の原則
- **戦略コードは研究と本番で完全に同一**。バックテスターと本番エンジンは同じ `Strategy` インターフェースを呼ぶ。「バックテストでは動いたが本番は別実装」を禁止する。これが乖離の最大要因。
- 各レイヤーはプロセス分離可能（データ取込が落ちても執行は生きる、逆も然り）。
- 全レイヤー間の通信は **イベント**（不変のデータクラス）で行う。

### 2.2 コンポーネント一覧

| コンポーネント | 責務 | 主要な設計上の注意 |
|---|---|---|
| Market Data Gateway | WebSocket で約定・板・funding・OI・清算を受信。REST でギャップ補完 | 再接続・シーケンス番号検証・ギャップ検知 |
| Data Store | 生データを無加工で永続化（Parquet 日次パーティション）。集計ビューを別途生成 | 生データは絶対に上書きしない（再現性） |
| Feature Engine | バー生成、特徴量計算（研究と本番で同一コード） | 時点 t の特徴量は t 以前のデータのみで計算（先読み禁止を型で強制） |
| Strategy Engine | 複数戦略を並列実行し、各戦略の「目標エクスポージャー」を出力 | 戦略は状態を持たない純関数に近づける |
| Portfolio Constructor | 戦略出力を束ね、ボラティリティ目標・相関・上限を考慮し目標ポジションに変換 | ここで資金配分・レバレッジを決める |
| Risk Gate | 発注前チェック。DD 上限・エクスポージャー上限・異常値・取引所状態 | 全注文がここを通過。バイパス不可 |
| OMS（注文管理） | 注文の状態機械、冪等な clientOrderId、レート制限管理 | 「二重発注」「幽霊注文」を構造的に防ぐ |
| Execution Algo | 目標ポジションと現ポジションの差分を、コスト最小で埋める | post-only 優先、TWAP/適応型、緊急時は taker |
| Reconciler | 取引所の真の状態と内部状態を定期照合 | 乖離時は「取引所が正」として内部を修正しアラート |
| Monitoring | メトリクス・ログ・アラート・ダッシュボード | 無音は異常。ハートビート必須 |

## 3. データ基盤

### 3.1 取得するデータ（本番・履歴ともに）

| データ | 用途 | 粒度 |
|---|---|---|
| 約定（trades） | バー生成、出来高特徴量、実現ボラ | ティック |
| 板（L2 orderbook） | 板の不均衡、スプレッド、深さ、スリッページ推定 | 更新差分 ＋ 定期スナップショット |
| ベスト気配（BBO） | 執行判断、マーク価格との乖離 | 更新ごと |
| 資金調達率（funding） | キャリー戦略、ポジション偏りの推定 | 8 時間 or 1 時間ごと ＋ 予測値 |
| 未決済建玉（OI） | レバレッジ蓄積、清算カスケードの予兆 | 1 分〜 |
| 清算（liquidations） | 強制決済の反転戦略 | イベント |
| 現物価格・インデックス価格・マーク価格 | ベーシス、プレミアム | 1 秒〜 |
| 取引所ステータス・メンテ情報 | リスクゲート | イベント |
| （将来）オンチェーン・ステーブルコイン発行量・ETF フロー | 中長期レジーム判定 | 日次 |

### 3.2 保存形式
- **生データ**: Parquet（ZSTD 圧縮）、`data/raw/{exchange}/{symbol}/{datatype}/{YYYY-MM-DD}.parquet`
- **集計データ**: 時間バー・出来高バー・ドルバーを事前計算し `data/bars/...` に保存
- **クエリエンジン**: DuckDB（研究）。ClickHouse は必要になってから。
- **メタデータ**: 各ファイルに取得時刻・ソース・スキーマバージョンを付与。データ修正は「新バージョンを追加」であって「上書き」ではない。

### 3.3 データ品質ゲート（自動）
- 欠損（ギャップ）検知: 期待レートに対する受信数の乖離
- 重複・順序逆転の検知（取引所の trade id 単調性）
- 異常値: 前値から ±10% のティックは要検証フラグ
- 時刻同期: 取引所タイムスタンプとローカル受信時刻を両方保存し、遅延分布を監視
- 品質レポートは日次で自動生成し、閾値超過はアラート

### 3.4 バー生成
- 時間バー（1m/5m/15m/1h/4h/1d）に加えて、**出来高バー／ドルバー**を生成する。
  - 理由: 暗号資産は活動量の変動が激しく、時間バーは統計的性質（正規性・自己相関）が不安定。情報到着量で区切ったバーの方が扱いやすい。
- バーには OHLCV に加えて、買い成行出来高、売り成行出来高、約定回数、VWAP、板不均衡の平均を含める。

## 4. 研究フレームワーク（エッジの発見と検証）

### 4.1 研究プロセス（固定手順）
1. **仮説の言語化**: 「なぜ」その非効率が存在し、「誰が」その反対側で損をしているのかを 3 行で書く。書けない仮説は検証しない（データマイニング防止）。
2. **特徴量定義**: 時点 t で観測可能なデータのみ。関数シグネチャで `as_of` を強制。
3. **ラベリング**: トリプルバリア法（利確・損切り・時間切れ）で「取引として意味のある」ラベルを作る。単純な「次の足の騰落」は使わない。
4. **単変量分析**: 特徴量とラベルの情報係数（IC）、分位ごとのリターン、時間安定性。
5. **モデル化**: ルールベース（解釈可能）を第一候補。機械学習は「特徴量が 10 個以上あり、非線形性が明らかなとき」のみ。勾配ブースティング（LightGBM）を上限とし、深層学習は当面使わない。
6. **バックテスト**: 第5章のバックテスターでフルコスト込み。
7. **検証**: ウォークフォワード ＋ CPCV（組み合わせパージド交差検証）。デフレートシャープで「試行回数」を罰する。
8. **審査**: 以下の合格基準を満たすまで本番投入禁止。

### 4.2 合格基準（研究段階）
- OOS シャープ > 1.5（コスト込み）かつ IS と OOS の劣化率 < 40%
- 手数料 2 倍・スリッページ 2 倍でも正のリターン（コスト感度）
- パラメータ ±30% 変更でも性質が保たれる（パラメータ安定性）
- 年別・レジーム別（強気／弱気／レンジ）で 1 年以上の大幅な負けがない
- 取引回数 ≥ 500（統計的有意性）
- 収益が上位 5% の取引に集中していない（テールに依存しない）

### 4.3 過学習・バイアス対策チェックリスト
- [ ] 先読みバイアス: 特徴量は `as_of` 制約下のみ。バー確定前のデータ使用禁止。
- [ ] 生存者バイアス: 上場廃止銘柄を含むユニバース
- [ ] データスヌーピング: 試行回数を記録し、デフレートシャープで補正
- [ ] 期間選択バイアス: 2020 年以降の全期間（COVID 暴落、2021 強気、2022 FTX 崩壊、2023〜24 回復、ETF 以降）を必ず含める
- [ ] 取引所固有バイアス: 単一取引所データで検証した戦略は別取引所で再検証
- [ ] コストの過小評価: 手数料は自分のティア、スリッページは板から推定、funding は必ず計上

## 5. バックテスター仕様

### 5.1 方式
- **イベント駆動**（ベクトル化バックテストは初期スクリーニングのみ）。
- 理由: 注文の部分約定、キュー位置、レイテンシ、資金調達、清算を正しく扱うにはイベント駆動が必須。

### 5.2 モデル化する現実
| 項目 | モデル |
|---|---|
| 手数料 | メイカー／テイカーを区別。ティアは設定値。リベートも扱う |
| スリッページ | 板スナップショットからの直接推定（利用可能時）。なければ「注文量／バー出来高」と「スプレッド」の関数 |
| レイテンシ | シグナル→発注→約定に固定＋確率的遅延を注入（例: 50ms ＋ 指数分布） |
| 指値の約定判定 | 保守的: 価格が指値を「突き抜けた」場合のみ約定。同値タッチは約定しない（キュー位置を考慮） |
| 部分約定 | 出来高の一定割合（例: 10%）までしか自分の注文は約定しない |
| 資金調達 | ポジション保有中は funding 時刻ごとに授受 |
| 清算・証拠金 | 維持証拠金率を計算し、清算価格到達で強制決済（＋清算手数料） |
| 取引所停止 | メンテナンス時間帯は発注不可としてシミュレーション |
| 最小ロット・価格刻み | 取引所仕様で丸める |

### 5.3 出力
- 取引ログ（全注文の生成〜約定〜決済までの完全な履歴）
- 資産曲線、DD 曲線、日次／月次リターン
- 統計: シャープ、ソルティノ、Calmar、勝率、ペイオフ、平均保有時間、回転率、手数料合計、スリッページ合計
- 帰属分析: 戦略別・銘柄別・ロング／ショート別・時間帯別
- 「バックテスト vs 実運用」比較用に、本番と同じフォーマットで出力

## 6. 戦略ポートフォリオ（エッジ仮説）

単一戦略で世界一にはなれません。相関の低い複数のエッジを束ねます。以下は初期候補で、それぞれ「なぜ存在するか」を明記します。

### 6.1 第1層: 中期トレンド追随（Time-Series Momentum）
- **仮説**: 暗号資産は情報の伝播が遅く、参加者の行動が群集的なため、数日〜数週間のトレンドが持続する。反対側で損をするのは、逆張りの裁量トレーダーと清算される過剰レバレッジ勢。
- **実装**: 複数ホライズン（例: 4h/1d/3d/1w）のリターン符号とボラ調整。ボラティリティ目標で規模を決める。
- **役割**: 強気・弱気の大きな動きを捕まえる「保険」。DD は大きいが、他戦略が負けるクラッシュ時に利益を出す。

### 6.2 第2層: 資金調達率キャリー（Funding Carry）
- **仮説**: 無期限先物の funding は、ロングに偏った小口投機家がショート側へ支払う「保険料」。極端な funding は平均回帰する。
- **実装**: funding が閾値超のとき反対側（例: 高い正の funding で先物ショート＋現物ロングのデルタニュートラル）。あるいは方向性戦略のポジションを funding 方向に傾ける。
- **役割**: 方向性リスクが小さく、レンジ相場でも稼ぐ。

### 6.3 第3層: 短期平均回帰（Microstructure Mean Reversion）
- **仮説**: 短期（数分〜数時間）では、流動性の一時的な不足によるオーバーシュートが平均回帰する。反対側は「急いで執行する」テイカー勢。
- **実装**: 板不均衡（OFI）、テイカー出来高の偏り、VWAP からの乖離、清算スパイクを使った逆張り。post-only 指値で流動性を提供する形で入る（手数料が利益になる）。
- **役割**: トレンド追随と負の相関。取引回数が多く、統計的に信頼できる。

### 6.4 第4層: 清算カスケード反転
- **仮説**: 大量清算は「価格の理由」ではなく「レバレッジの理由」で起きるため、行き過ぎた価格は数分〜数時間で戻る。
- **実装**: 清算量・OI 急減・funding 急変を検知し、逆方向に小さく入る。
- **役割**: イベント型。回数は少ないがペイオフが大きい。

### 6.5 第5層（第2段階）: クロスセクション・モメンタム／リバーサル
- **仮説**: アルトコイン間の相対的な強弱は継続する（数日）一方、極端な相対乖離は戻る（数時間）。
- **実装**: 上位 20〜30 銘柄でランク付けし、上位ロング／下位ショートの市場中立ポートフォリオ。
- **役割**: BTC の方向に依存しない収益源。

### 6.6 除外するもの（当面）
- 純粋マーケットメイク: レイテンシ競争。取り組むなら専用インフラ後。
- ニュース／SNS センチメント: データ品質と検証の難しさ。第3段階以降。
- 深層学習による価格予測: サンプル数と非定常性の問題。エッジの説明もできない。

### 6.7 戦略の合成
- 各戦略は「目標エクスポージャー（−1〜+1）」と「確信度」を出力。
- ポートフォリオ構築で、(a) 戦略ごとのボラティリティ目標、(b) 戦略間の相関に基づく重み（リスクパリティを起点）、(c) 直近の実績によるゆるやかな重み調整（ただし急激な切り替えはしない）を行う。
- 総レバレッジ上限、銘柄ごとの上限、方向ごとの上限を強制。

## 7. リスク管理

### 7.1 階層的リスク制御
| レイヤー | 制御 | 発動時の動作 |
|---|---|---|
| ポジション | 1 銘柄あたり最大エクスポージャー（例: 資産の 30%） | 超過分は発注拒否 |
| 戦略 | 戦略ごとの DD 上限（例: −8%） | その戦略を停止し、他戦略は継続 |
| ポートフォリオ | 総 DD ラダー: −5% で規模半減、−10% で 1/4、−15% で全停止 | 自動。人間の承認なしに再開しない |
| 日次 | 日次損失上限（例: −3%） | 当日は新規発注停止、既存はクローズのみ |
| 総レバレッジ | 上限（例: 2 倍） | 超過分は削減発注 |
| 取引所 | 単一取引所への資金集中上限（例: 60%） | 分散。取引所破綻リスク（FTX の教訓） |
| 異常検知 | 価格が 1 分で ±5%、データ遅延 > 5 秒、板が空 | 新規停止、既存はホールド or クローズ（戦略設定による） |
| システム | ハートビート途絶、照合乖離、例外多発 | キルスイッチ: 全注文取消 → ポジションを安全側へ |

### 7.2 ポジションサイジング
- **ボラティリティ・ターゲティング**: 年率目標ボラ（例: 25%）に対し、直近の実現ボラ（EWMA）でスケール。
- **ケリー基準の分数**（1/4 ケリー以下）を上限として適用。
- 確信度による調整は「離散的（0 / 0.5 / 1.0）」にし、微調整による回転率増を避ける。

### 7.3 キルスイッチの設計
- 手動: CLI 一発 ＋ スマホからの通知返信で全停止できること。
- 自動: 上記トリガー。
- 「停止後にどうするか」を事前に決めておく: 既定は「全注文取消 ＋ ポジションをテイカーでクローズ」。ただしボラ極大時はクローズ自体が損失を生むので、「ヘッジ（反対側の先物）」を選択肢として持つ。

## 8. 執行（Execution）

### 8.1 原則
- 目標ポジションと現ポジションの **差分** を埋める（戦略が「買え／売れ」ではなく「このポジションでいたい」を言う）。
- コスト最小化: 既定は **post-only 指値**（メイカー）。一定時間で約定しなければ価格を追従、緊急度に応じてテイカーへエスカレーション。
- 執行アルゴは緊急度（urgency）をパラメータに持つ: 平均回帰戦略は「約定しなければ諦める」、トレンド戦略は「必ず約定させる」。

### 8.2 OMS（注文管理）の状態機械
```
NEW → SUBMITTED → (PARTIALLY_FILLED)* → FILLED
                ↘ CANCEL_REQUESTED → CANCELED
                ↘ REJECTED
                ↘ UNKNOWN（通信断。照合で解決するまで新規発注禁止）
```
- clientOrderId は決定論的に生成（戦略・銘柄・意図・時刻のハッシュ）し、**冪等**に再送できるようにする。
- 「UNKNOWN」状態を第一級の状態として扱う。通信断で注文が通ったか分からない時に再送すると二重発注になる。

### 8.3 照合（Reconciliation）
- 毎 N 秒、取引所の「ポジション・残高・未約定注文」を REST で取得し、内部状態と突合。
- 乖離があれば取引所を正とし、内部を修正、アラート。乖離が閾値を超えたら安全停止。
- WebSocket のユーザーデータストリームを主、REST 照合を従とする。

### 8.4 レート制限・接続
- 取引所のレート制限をトークンバケットで内部管理。制限到達前に自主的に抑制。
- WebSocket 再接続は指数バックオフ ＋ ジッター。再接続時は必ずスナップショットを取り直す。
- 時刻同期: NTP ＋ 取引所サーバ時刻との差分を常時監視。

## 9. 運用・監視

### 9.1 メトリクス（Prometheus 形式）
- PnL（実現・未実現）、エクスポージャー、レバレッジ、DD
- 注文数、約定率、メイカー比率、平均スリッページ、リジェクト数
- データ遅延、WS 再接続数、REST エラー率
- 戦略ごとのシグナル値・ポジション

### 9.2 アラート（重大度別）
- **P0（即時・電話級）**: キルスイッチ発動、照合乖離、DD 閾値到達、ハートビート途絶
- **P1（数分内）**: データ遅延、レート制限到達、リジェクト連続
- **P2（日次レポート）**: 品質レポート、バックテスト乖離、コスト統計

### 9.3 ログ
- 構造化ログ（JSON）。全イベント（データ受信・シグナル・注文・約定）を永続化し、**任意の時点の判断を後から完全再現**できるようにする。

### 9.4 デプロイ
- Docker Compose（データ取込／戦略エンジン／執行／監視をコンテナ分離）
- 設定は環境変数 ＋ YAML。秘密情報（API キー）は環境変数か秘密管理ツール。**リポジトリには絶対に置かない**。
- API キーは「取引のみ・出金不可・IP 制限」で発行。

## 12. 正直な注意事項

- バックテストで「世界一」に見える戦略は毎日生まれ、実運用でほぼ全て消えます。本設計はその「消える理由」を一つずつ潰す構造にしています。それでも利益は保証されません。
- 暗号資産市場は取引所リスク（破綻、ハッキング、出金停止）が株式市場より桁違いに大きい。資金の分散と、取引所に置く資金の上限は戦略以上に重要です。
- 税務・法規制は居住国で大きく異なります。設計の前提（取引所選択、レバレッジ）に影響するので、決定事項 D-01 で必ず確認します。
