# バックテスター詳細仕様（v0.1）

設計書 5 章を実装可能な粒度まで落とす。目的は「本番で起きることを漏れなく再現し、バックテストと実運用の乖離を最小化する」こと。

---

## 1. 基本構造

### 1.1 イベント駆動ループ
```
for event in merged_stream(bars, funding, (trades|book のオプション)):
    clock = event.ts
    engine.on_event(event)            # 未約定注文の約定判定、funding 授受、清算判定
    if event is BarClose:
        features = feature_engine.update(bar)        # as_of = bar.close_ts
        targets  = strategy.on_bar(features, state)  # 目標エクスポージャー
        orders   = executor.plan(targets, positions, book_or_bar)
        oms.submit(orders, available_at = clock + latency)
    ledger.mark_to_market(clock)
```
- **イベントの順序**: 同時刻なら `Funding → BarClose → OrderFill`。バー確定より前に、そのバーの中で起きた約定を処理してはいけない。
- **レイテンシ**: 注文はシグナル時刻 + `latency`（既定 300ms、確率的に上乗せ）以降にしか市場に届かない。バー足でのバックテストでは「次のバーの始値以降」に単純化するが、ティックモードでは実時刻で判定する。

### 1.2 二つのモード
| モード | 入力 | 用途 | 約定判定の精度 |
|---|---|---|---|
| **Bar** | 時間バー or ドルバー | 戦略のスクリーニング、パラメータ探索 | 保守的近似（下記 3 章） |
| **Tick** | 約定列（＋板があれば板） | 執行アルゴの検証、コストの最終確認 | 高い（キュー位置モデル） |

戦略コードは両モードで同一。モード差は約定判定エンジンにだけ現れる。

## 2. 口座・ポジションモデル（無期限先物）

- 証拠金通貨: USDC（Hyperliquid）/ USDT（CEX）。損益はすべて証拠金通貨建て。
- ポジション: 銘柄ごとに符号付き数量 `q`、平均建値 `p_avg`。
- 未実現損益: `q × (mark − p_avg)`。マーク価格はバーの close（Bar モード）または直近約定（Tick モード）。
- **資金調達**: funding 時刻ごとに `−q × mark × rate` を残高に加減（正の rate はロングが支払う）。
  Hyperliquid は 1 時間ごと、Binance/Bybit は 8 時間ごと。データの `interval_hours` に従う。
- **維持証拠金と清算**: `equity < Σ |q| × mark × mmr` で清算。`mmr` は取引所・レバレッジ帯で異なるので設定値（既定は Hyperliquid の最大レバレッジから `1/(2×maxLev)` を近似）。清算時は全ポジションをテイカーで決済し、清算手数料（既定 1%）を課す。**清算は損失ではなく「バックテスト失敗」として扱い、レポートで赤字強調する。**
- **レバレッジ上限**: 制約分析 3.2 に従い、名目 / equity が 2.5 を超える注文はリスクゲートで拒否（本番と同じコード）。

## 3. 約定モデル（Bar モード）

| 注文種別 | 約定条件 | 約定価格 |
|---|---|---|
| 成行（taker） | 次バー始値で即約定 | `open × (1 ± slippage)` |
| 指値（post-only） | 買い: 次バー以降の `low < limit`（**同値タッチは不約定**）。売り: `high > limit` | `limit`（メイカー手数料） |
| 指値（クロスする価格） | post-only では拒否。IOC なら成行扱い | |

- **部分約定**: 1 バーで約定する上限は `bar.volume × participation`（既定 5%）。残りは次バーへ持ち越し。
- **スリッページ（成行）**: `slippage = half_spread + impact`。
  - `half_spread`: 銘柄ごとの設定値（Hyperliquid 実測で較正。BTC/ETH は 0.5bp 前後を初期値）。
  - `impact = k × sqrt(order_notional / bar_quote_volume)`、`k` は既定 0.1（保守的。実約定で較正）。
- **指値の追従**: 執行アルゴが「N バー未約定なら価格を 1 tick 寄せる」「M バーで諦めて成行」を担う（4 章）。
- **フィルタ**: 数量は `InstrumentSpec.round_qty`、価格は `round_price`。`min_notional` 未満は拒否。本番と同じ検証関数を呼ぶ。

### 3.1 Tick モードの追加
- 指値のキュー位置: 発注時点の同一価格の板量を前に置き、`その後の同価格での約定量 > 板量 + 自注文量` で約定。板がなければ `同価格での約定量 > 自注文量 × 2` を保守的代替とする。
- 成行はその時点の板を消費して VWAP で約定。板がなければ直近約定 ± half_spread。

## 4. 執行アルゴ（研究と本番で共通）

`Executor.plan(target_qty, current_qty, urgency)`:
1. `delta = target − current`。`|delta| × price < min_notional` なら何もしない（ドリフト許容）。
2. `urgency = LOW`: post-only 指値を最良気配に置く。3 バー未約定なら 1 tick 寄せ、10 バーで取消（諦める）。
3. `urgency = NORMAL`: 同上だが 5 バーで成行にエスカレーション。
4. `urgency = HIGH`（損切り・キルスイッチ）: 即成行。
戦略は `urgency` を目標と一緒に返す。

## 5. コストの計上（漏れを許さない）

| コスト | 計上 |
|---|---|
| 手数料 | 約定ごとに `notional × fee(maker/taker)`。ティアは設定 |
| スリッページ | 約定価格に織り込み済み。別途「理論価格との差」を集計してレポート |
| 資金調達 | 2 章のとおり |
| 清算手数料 | 2 章のとおり |
| 出金・ブリッジ | バックテスト対象外だが、レポートの注記に固定額として表示 |

**コスト感度テスト**: 手数料 ×2、スリッページ ×2、レイテンシ ×3 の 3 通りを自動で回し、結果を並べて出す。いずれかで負に転じる戦略は不採用。

## 6. 先読み防止（構造で強制）

- 特徴量関数は `(bars_up_to_close_ts, as_of) → features` の形しか許さない。バーの `close_ts_ms > as_of` を含む DataFrame を渡すと例外。
- 戦略は「確定したバー」のみ受け取る。バー確定は `close_ts_ms` 到達時であり、ラベル `open_ts_ms` の時点ではない。
- 未来の funding 率は使えない。次回 funding の「予測値」は、本番 API が提供する時点以降のみ特徴量として許可（当面は不使用）。
- **シャッフル検定**: 特徴量の時間軸をランダムにずらした入力で戦略を回し、性能が消えることを CI で確認する（消えなければ先読みか、バグ）。

## 7. 検証プロトコル

### 7.1 データ分割
- 学習/探索期間: 2020-01 〜 2024-06
- 検証（OOS-1）: 2024-07 〜 2025-06
- 最終テスト（OOS-2）: 2025-07 〜 現在（**1 戦略につき 1 回しか見ない**。見たら記録する）

### 7.2 ウォークフォワード
- 学習窓 18 か月 → 検証窓 3 か月を 3 か月ずつスライド。各窓でパラメータを再推定し、検証窓の成績のみを連結して評価。

### 7.3 CPCV（組み合わせパージド交差検証）
- 期間を 8 ブロックに分け、2 ブロックをテストとする全 28 通り。境界では **パージ**（テスト前後 保有期間分を学習から除外）と **エンバーゴ**（テスト直後 1 週間を除外）。
- 28 通りのシャープ分布を出し、中央値と下位 10% を報告。

### 7.4 デフレートシャープ
- 試したパラメータ組み合わせの数 `N` と、シャープ分布の分散から、観測シャープが偶然で出る確率を計算。`p < 0.05` を合格ライン。
- **試行回数は自動記録**: バックテスト実行のたびに `research/trials.jsonl` に戦略 ID・パラメータ・結果を追記し、手作業で消せないようにする。

### 7.5 合格基準（設計書 4.2 の再掲、数値確定）
| 項目 | 基準 |
|---|---|
| OOS シャープ（コスト込み） | ≥ 1.5 |
| IS→OOS 劣化率 | < 40% |
| コスト ×2 でのリターン | > 0 |
| パラメータ ±30% | シャープの符号と桁が不変 |
| 取引回数 | ≥ 500 |
| 上位 5% の取引の利益寄与 | < 50% |
| 年別 | どの暦年もシャープ > 0（2022 年を含む） |
| デフレートシャープ p 値 | < 0.05 |

## 8. 出力

- `trades.parquet`: 注文 ID、戦略、銘柄、方向、発注時刻、約定時刻、数量、価格、手数料、スリッページ、urgency、約定までのバー数
- `equity.parquet`: 時刻、残高、未実現、equity、エクスポージャー、レバレッジ、DD
- `summary.json`: 7.5 の全指標 ＋ 手数料合計、funding 合計、スリッページ合計、清算回数、回転率、平均保有時間、メイカー比率
- `attribution.parquet`: 戦略 × 銘柄 × 方向 × 時間帯 × 年 の損益
- 本番の `live/` も同じスキーマで出力し、**同一期間の比較レポート**（乖離検出）を自動生成する。
